IMP-1046

 | 

Removal of non-standard fields from Flags API

 | 

Duplicated and ambiguous fields are being removed from the Flags API:- The `name` field in the FlagDefinition resource - replaced by `id` field- The `creation_timestamp` field in the Flag resource - renamed to `create_timestamp`\- The `is_active` field in the Flag resource - functionality has been replaced by Flags with Value `FLAG_VALUE_OFF`\- The `include_inactive` field in the ListFlagsRequest - with the removal of the `is_active` field, this filter becomes redundant - note that the default behaviour for this endpoint will include the Flags that were previously considered inactive.- The `effective_timestamp` field in the ListFlagsRequest - with the removal of the `is_active` field, this filter can be replaced by the `effective_timestamp_range` filter- Support for `is_active` in the UpdateFlagRequest - with the removal of the `is_active` field, this functionality becomes redundant - The `payment_device_ids` field in the ListFlagsRequest - with the removal of Payment Device support in the Flags API, this field will become redundant

IMP-800

 | 

Vault traces format: deprecate Jaeger format with otlp-collector upgrade

 | 

The format in which Vault exports traces changes from Jaeger to the more widely used OTLP and OTLP-HTTP.In order to address security vulnerabilities on the opentelemetry-collector service, we are upgrading it to the latest version, which completely dropped support for the Jaeger trace export format.Please migrate to the new format by updating your Values: leave "tracing.exporter.jaeger-endpoint" empty, use one of the new values instead: "tracing.exporter.otlp\_endpoint", "tracing.exporter.otlp\_http\_endpoint".As a temporary solution, an additional opentelemetry-collector component can be configured to convert otlp traces into Jaeger format.

 |

TM-89254

 | 

PUT v1/parameter-values can set effective-to timestamp to be the same as effective-from

 | 

This bug allows a Parameter Value to have its `effective_to_timestamp` updated to be the same as its `effective_from_timestamp` by specifying it as one nanosecond after it. This should not be permitted and any value like this will not appear in the timeseries provided to a contract hook. The fix will allow an update to be rejected if the new effective-to timestamp is in the same microsecond as the effective-from.

 |
| 

TM-91547

 | 

Failed directives from post\_parameter\_change\_hook treated as internal errors

 | 

If any directives returned by the post\_parameter\_change\_hook (schedule modifications, posting instructions, notifications) fail to be committed, Vault Core incorrectly treats it as an internal error. This will block any further executions of the hook for that account until a retry of the hook eventually succeeds. Converting the affected account to a new Product Version that will not produce the directives which fail would work around this. This change has fixed how the error is treated, preventing further executions from being blocked. This does not apply to executions that arise from using the v1/account-updates API, only the v1/parameter-values API.

 |

@requires "latest live" fetches an interval in Vault 5 compared to a live observation in Vault 4, for both postings and balances

 | 

The behaviour in the Contracts Language for balance fetching using @requires(balances="latest live") and @requires(postings="latest live") has been fixed to match the behaviour in Vault 4.  
  
In previous versions of Vault 5, "latest live" returned balance entries for each balance coordinate from the effective time to now. upgrade-path-migrator does not always respect inactive period

 | 

The upgrade-path-migrator Deployment in 4.7.x does not respect the upgrade\_path.inactive\_period field in the values.yaml, which is used to pause its activity to avoid overloading the database during peak load periods such as end of day. There are two scenarios, when the inactive period is not respected:
