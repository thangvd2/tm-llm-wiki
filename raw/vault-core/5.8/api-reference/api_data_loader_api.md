error

The guidance within this section of the Vault Portal contains API specifications for the Data Loader API, including example messages covering both requests / streamed events.

Other content is available in the wider Vault Portal covering other migration-related topics, which you should read in conjunction with the content here.

Other API specifications (inc. example messages / requests):

-   [Posting Migration API specifications](/vault-core/5-8/EN/api/postings_api#posting_migration_api)
    

Migration API functional behaviour (inc. message lifecycle, error handling, etc.):

-   [Using Vault Core’s migration APIs](/vault-core/5-8/EN/environment_and_installation/migrating_to_vault)
    

How to deliver a successful migration programme (part of the Vault Core Delivery Framework), including migration strategies.

-   [Vault Core Delivery Framework - Migration Workstream](/delivery-framework/latest/EN/delivery_workstream/migration)
    

The Data Loader API is Vault Core’s strategic solution for migrating existing back-book data to Vault Core:

-   The [Data Loader Kafka (Streaming) API](/vault-core/5-8/EN/api/data_loader_api#data_loader_kafka_streaming_api) is used to migrate data into Vault Core. Usually when Thought Machine colleagues or the documentation within the Vault Portal refers to the 'Data Loader API' they are referring to this Kafka streaming API element specifically.
    
-   The [Data Loader REST API](/vault-core/5-8/EN/api/data_loader_api#data_loader) is used to query data that you have previously sent for migration into Vault. It does not support REST Creation (only querying previously created data) and should be used only for low-volume checks and not full migration event reconciliations.
    

The exception to the comment above regarding the 'strategic solution' is the migration of Postings, which are instead migrated using the [Posting Migration API](/vault-core/5-8/EN/api/postings_api#posting_migration_api), which is documented separately.

#### [](#key_data_loader_concepts "Copy link to heading")Key Data Loader concepts

 
| Concept | Description |
| --- | --- |
| 
Resource

 | 

A *Resource* is an entity of data within Vault Core; for example a single Customer 'resource' is a single customer record including all associated objects and fields, an Account 'resource' is a single account record, and so on.

The Data Loader supports the migration of a specific selection of Vault Core resources. For more information, see the Supported Resources section [CreateResourceBatches](/vault-core/5-8/EN/api/data_loader_api#createresourcebatch_requests).

 |
| 

Resource Batch

 | 

You send resources to the Data Loader in *Resource Batches*; these act as containers for one or more resources, which are optimised for load performance.

The Data Loader is asynchronous in the way it processes resources. The ordering and timing of when resources are loaded into Vault is independent of when you submit them, and you will receive updates via streamed events to keep you informed of their progress.

 |
| 

Dependency Group

 | 

*Dependency Groups* are logical links between associated resources which can enforce the order in which these resources are loaded to Vault. Dependency Groups can span resource batches and include any resource types supported by the Data Loader.

For example, dependency groups can be used to prevent an Account resource from loading until a dependent Customer resource has been received and loaded successfully to Vault. Some dependencies are inherent in Vault based on its logical data model; others you can set yourself.

 |

#### [](#message_formats "Copy link to heading")Message formats

The supported message formats for the Data Loader Kafka (Streaming) API are JSON or Google Protobuf. JSON is the most commonly used Data Loader API message format because it is easier to integrate ETL tooling with.

The required format is set when your Vault Core instance is configured and defaults to Proto. See the [Installing the Migration API](/vault-core/5-8/EN/environment_and_installation/migrating_to_vault/intro#selecting_json_versus_proto_api_formats) guidance for more detail on how to change the message format.

 | 

The `resource` object comprises:  

\- A snapshot of the resource’s fields and values shortly after they arrived at the Data Loader but prior to being loaded. This is effectively a copy of the original request message, but may contain some additional fields not set on the original request message with null or defaulted values added by the Data Loader. E.g. see the `account_resource` below `type` field - in the `resource` object it defaults to `ACCOUNT_TYPE_UNKNOWN` as it is an output only field.  

\- A set of Data Loader wrapper fields that will always show a PENDING status, which can be ignored (the resource\_status present in the vault\_resource\_loaded object is the single source of terminal load outcome of LOADED or FAILED).

 |
| 

`vault_resource_loaded`

 | 

Uses the same field and object structure as shown in the [Resource](/vault-core/5-8/EN/api/data_loader_api#resource) GET Response example (REST API)

 | 

The `vault_resource_loaded` object comprises:  

\- A snapshot of the resource’s fields and values after they had attempted to be migrated to Vault Core. For FAILED resources these are identical to the request (as nothing has changed since the request), and for LOADED resources they will reflect the fields and values that were actually successfully loaded into the Vault Core database, including output only fields. E.g. see the `account_resource` below `type` field - in the `vault_resource_loaded` object it has been set by Vault Core to `ACCOUNT_TYPE_CUSTOMER`.  

\- A set of Data Loader wrapper fields that will contain the load status for LOADED or FAILED resources.

 |
