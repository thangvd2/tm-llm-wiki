There are various groups of APIs that provide key parts of Vault Core functionality. This section describes the general characteristics of these APIs.

### [](#api_types "Copy link to heading")API Types

The Vault Core APIs consist of two types of APIs:

-   The Vault Core *REST APIs* use predictable and resource-oriented URLs with standard HTTP methods and status codes. Responses are in JSON format.
    
-   The *Streaming APIs* use Kafka to emit messages to a series of Kafka topics. These messages are events which reflect mutations of resources in Vault Core.

### [](#http_request "Copy link to heading")HTTP Request

#### [](#headers "Copy link to heading")Headers

The API uses the following request header:

-   The Authorization header includes the API key and session tokens.
    

Each request can optionally include:

-   An `X-On-Behalf-Of-Customer-ID` header containing the ID of the Vault Core customer that the service account is making the request for.
    
-   An `X-On-Behalf-Of-Employee-ID` header containing the ID of the bank employee that the service account is making the request for.
    
-   An `X-On-Behalf-Of-Employee-Email` header containing the email of the bank employee that the service account is making the request for.
    

These headers are used only by the Audit and Action Logs services. The values assigned to the headers will be in the corresponding logs generated by the request.

These headers won’t change any of the functionality of the underlying API call. Requests will behave identically whether they’re included or not.

#### [](#request_body "Copy link to heading")Request body

The request body for most GET, POST and PUT calls, must be in JSON format unless stated otherwise.

### [](#update_masks "Copy link to heading")Update masks

When you’re updating resources, you must provide update masks for the fields being updated. If a field mask references a property of a nested object, the object must exist on the request but it can be empty.

For example, if an update mask contains the path `details.first_name`, `first_name` can be empty but the `details` object must not be empty.

### [](#omitted_by_default "Copy link to heading")Omitted by default

By default, fields marked as `omitted by default` will not be automatically populated because their content is either large in size or costly to compute. These fields may be populated by passing the query parameter `fields_to_include` with values from `IncludeField`.

Vault Core API access control is achieved using one of two methods. Use only one method in each request:

-   JSON Web Tokens (JWTs) as bearer tokens (the recommended method)
    
-   Authentication Tokens (legacy method) using Service Account Tokens

### [](#json_web_tokens "Copy link to heading")JSON Web Tokens

This section describes the usage of JWT tokens.

#### [](#getting_a_jwt "Copy link to heading")Getting a JWT

JWTs should be generated according to the best practice outlined in [JWT Generation Process](/vault-core/5-8/EN/vault_core_overview/vault_security#jwt_generation_process).

For the JWT to be accepted, the following JWT claims MUST be provided:

-   Issued at timestamp (`iat`) - the number of seconds since the Unix epoch, defining when the JWT was issued.
    
-   Expiry timestamp (`exp`) - the number of seconds since the Unix epoch, defining when the JWT expires.
    
-   Subject identifier (`sub`) - a unique identifier for the actor associated with the JWT.
    

The following claim *must* be provided if there is more than *one* issuer configured:

-   Issuer (`iss`) - a string that identifies the principal that issued the JWT.
    

The following claims are optional, but recommended:

-   Not before timestamp (`nbf`) - the number of seconds since the Unix epoch, defining when the JWT becomes valid.
    
-   Audience (`aud`) - an audience string value for the JWT to be verified against. Typically this is a URL, but it may be any string. `aud` limits the scope of where a JWT may be used. If set on the token, Vault Core validates this against the configured audience values.
    
    For more information, see [JWT Audience](/vault-core/5-8/EN/vault_core_overview/vault_security#jwt_audience).
    

In addition to these claims, the JWT should include any claims necessary for the [OPA Policy](/vault-core/5-8/EN/reference/policies/opa-policies#overview_opa) attached to the API gateway to authorise the request.

For example, Vault Core provides the following default Rego policy attached to the API:

For this policy to accept a request, the JWT needs to include either:

-   an `scp` claim - this is a JSON array
    
-   a `scope` claim - this is a JSON space-separated string
    

The policy requires that at least one of these claims contains an API scope that is associated with the API endpoint that is the destination of the request.

#### [](#bad_request "Copy link to heading")Bad Request

`BadRequest` describes the violations in the clients request often due to invalid or missing field values.

Commonly used for errors with the following codes:

-   `INVALID_ARGUMENT`
    

Indicated by `@type`

A `BadRequest` includes one or more `field_violations`.

A violation’s `violation_type` indicates the type of validation error is generic across all APIs. These include but are not limited to `INVALID_FORMAT`, `INVALID_VALUE`, `REQUIRED_FIELD`, `DUPLICATE_FORMAT`.

The field that caused the violation is specified using its JSON path name in the `field` field.

In addition each violation includes a `description` field which contains a human-readable message describing the error. Wording of descriptions may change between Vault Core releases.

#### [](#invalid_code "Copy link to heading")Invalid Code

`InvalidCode` describes violations from source code in the client request, due to syntax errors or operations that are disallowed by the execution environment that the code will run within.

Commonly used for errors with the following codes:

-   `INVALID_ARGUMENT`
    

Indicated by `@type`

An `InvalidCode` detail includes one or more `violations`. Each of which can contain:

-   `violation_type` - indicating the broad category of error. It is limited to a discrete set offending values that includes, but is not limited to: `DisallowedError`, `DefinitionError`, `SyntaxError`.
    
-   `code` - a snippet of the offending code which may or may not be present.
    
-   `description` - a human readable description, explaining the nature of the violation.
    
-   `lineno`, `offset`, `end_lineno`, and `end_offset` - zero or more of these may be present to indicate the location within the source code where the violation occurred, if the location is known and applicable.
    

#### [](#precondition_failure "Copy link to heading")Precondition failure

`PreconditionFailure` describes what preconditions have failed; a precondition is defined as:

A condition or predicate that must always be true just prior to the execution of some section of code or before an operation in a formal specification.

Commonly used for errors with the following codes:

-   `FAILED_PRECONDITION`
    

Indicated by `@type`

A `PreconditionFailure` includes one or more `violations`. A violation’s `violation_type` indicates what precondition was violated and is defined for each API Method. In addition each violation can also include `metadata` which may include further information, such as resource state, to help identify the issue.

Please see Method specific documentation for violation types, what causes them and the available metadata.

#### [](#resource_information "Copy link to heading")Resource information

`ResourceInfo` describes what resources produced the error when processing the request

Commonly used for errors with the following codes:

-   `NOT_FOUND`
    
-   `ALREADY_EXISTS`
    

Indicated by `@type`

A `ResourceInfo` includes an array of `resource_ids`. For example, if multiple resources were not found during a `BatchGet` request the missing resource ids would be included in this field.

## [](#idempotency "Copy link to heading")Idempotency

All actions which modify states in Vault Core’s APIs are *idempotent*. This means they’re safe to retry and will produce exactly the same result despite having been requested before. Idempotency enables solutions to be built which are resilient to network and infrastructure problems, providing a better experience for the user.

Some requests can’t determine whether you meant to make two identical calls or to retry a single call (for example upon making a transfer or payment). You can indicate this using the `request_id` field which is present in all state-modifying requests.

The value of this field must be unique for all distinct calls to the API. For this reason we suggest using something like UUIDv4 to ensure uniqueness.

When you want to:

-   Retry the same request, use the same `request_id`
    
-   Make a similar but distinct request, use a new value for the `request_id`
    

chat\_bubble

From Vault Core 5.0, `request IDs` may be purged when they are at least seven days old. A new request will be generated if a request ID is reused after the original has been purged. This does not apply to Configuration Resources.

Determining whether or not to retry a request should be based on the HTTP response code. For further information, see the Status codes section in the [Overview](/vault-core/5-8/EN/api/overview#overview).

## [](#pagination_guarantees "Copy link to heading")Pagination guarantees

### [](#overview_2 "Copy link to heading")Overview

In Vault Core, resources retrieved using a List endpoint are displayed using pagination defined by a page token that is included in subsequent API requests. If the resources that are being retrieved change while pagination is in progress, the resources displayed will depend on the pagination data consistency guarantee associated with the List endpoint used.

### [](#pagination_data_consistency_guarantee_levels_for_list_endpoints "Copy link to heading")Pagination data consistency guarantee levels for List endpoints

If the resources retrieved change during pagination and the List endpoint offers:

-   Best-effort consistency guarantee, responses may not contain all entries and/or may contain duplicate or inconsistent entries; do not use List endpoints of this level to calculate accurate aggregates via pagination.
    
-   Page-level consistency guarantee, responses may contain entries of varying ages. Pagination is more robust to concurrent data mutation, but it may be temporally inconsistent, as the requests are not pinned against the state of the system at a particular point in time; do not use List endpoints of this level to retrieve snapshots of the system for a given timestamp.
    
-   Snapshot consistency guarantee, responses will contain entries as of a given timestamp. Pagination is robust to concurrent data mutation and is temporally consistent, as the requests are pinned against the state of the system at a particular point in time; do not use List endpoints of this level to retrieve the most up-to-date view.
    

chat\_bubble

See the API documentation for each List endpoint to view its pagination data consistency guarantee type.

## [](#using_the_streaming_apis "Copy link to heading")Using the Streaming APIs

### [](#overview_3 "Copy link to heading")Overview

Vault Core uses a data streaming architecture across all components to enable near real-time data publishing. The Vault Core data streaming architecture provides the advantages of a modern, event-driven, Kafka-based data architecture:

-   Near real-time event sourcing through streaming
    
-   Guaranteed at least once delivery
    
-   Ability to scale to large volumes through Kafka
    
-   Full access to underlying Vault Core state changes
    
-   Subscribe as many consumers as is needed without extra burden on the core
    
-   Granular access to an extensible data model
    

This data can have various uses. For example, to:

-   Improve customer loyalty through real-time tailored insights
    
-   Reduce risk and free up capital through continuous liquidity monitoring and management
    
-   Increase revenue through contextual, personalised product offerings
    
-   Enable real-time general ledger and reconciliation integrations
    

### [](#streaming_apis "Copy link to heading")Streaming APIs

Vault Core uses two types of API to enable interaction with the system and the data held within it:

-   RESTful APIs for synchronous interaction
    
-   Streaming APIs for asynchronous interaction

#### [](#data_is_available_from_all_components "Copy link to heading")Data is available from all components

Each component of Vault Core provides an outbound Streaming API that uses a push mechanism to provide data in near real-time for use in external systems. All Vault Core Platform components stream their state change in near real-time: Kernel, Payments Hub, Workflow Engine, and so on, allowing the state of each Vault Core component to be reflected in external systems.

#### [](#integration_via_kafka_topics "Copy link to heading")Integration via Kafka topics

The Streaming APIs are based on Apache Kafka, with each event type, such as a Posting or a balance update, streamed from a dedicated topic. Any number of external systems can subscribe to these topics to enable the use of Vault Core data in systems for use cases such as storage, data analysis, machine learning, reporting, and more.

#### [](#benefits_of_streaming_apis "Copy link to heading")Benefits of Streaming APIs

-   Operational efficiency: Removes the burden that is typically put on the operational resources of legacy cores and enables the ability to scale to large volumes of transactions. Removes the need for downtime or reduced operational processing by taking a 24/7, real-time data publishing approach.
    
-   Respond to change: Increases the bank’s responsiveness to business change by enabling real-time actions to be taken based on streamed events. Intra-day financial positions, real-time fraud detection, and obtaining up-to-date views on financial and operational risk can be achieved with real-time data.
    
-   Advanced analytics: Near real-time granular data enables advanced analytic capabilities to be adopted, such as machine learning, by enabling training of models in real time.
    
-   Ease of integration: Event data is product-agnostic, enabling changes to be made to a product’s underlying Smart Contract without need to alter the downstream integrations that receive these events. Similarly, integrations can be changed without intervening in product functionality.
