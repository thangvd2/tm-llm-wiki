TM-72898

 | 

\[Contracts Simulation\] Enable Sim Debug Logging in Smart Contracts, plus implement in Contract Modules and Supervisor Contracts

 | 

Simulation Logging allows Contract Writers to add debug logs to Smart/Supervisor Contracts and Contract Modules. The logs are returned as part of the output when calling the SimulateContracts endpoint on the Core API. This feature allows Smart Contracts to be debugged without using other features not intended for this purpose, such as contract notifications. Logs will be returned in all cases except for when Supervisor Contracts raise an error.

TM-86485

 | 

Unsetting optional parameters via v1/account-updates will publish an event for a Parameter Value that was not created

 | 

Unsetting an optional instance parameter via the v1/account-updates endpoint on Vault Core 5.0 prior to this fix will result in a message on vault.core\_api.v1.parameters.parameter\_value.events for a Parameter Value that was not actually created. This event will also be present in the v1/journal-events API.This is now fixed so that no such events will be produced; however, events generated before installing 5.0.3 will still be present via the v1/journal-events API, and will be replayed if using our disaster recovery functionality.

 |
| 

TM-86322

 | 

CL3 → CL4 product version AccountUpdate cannot recover from transitional state

 | 

Account conversions between Contract Language V3 and Contract Language V4 may encounter failures midway through the conversion pipeline. In such cases, certain resources may already be created, while others are pending creation. Consequently, a retry becomes necessary. This fix ensures that the retry process successfully completes the conversion, addressing the incomplete conversion issue.

 |
| 

TM-85671

 | 

Account processor does not automatically recover when embedded contract execution workers get stuck

 | 

In the event that a long-running smart contract hook is executed when modifying an account via the v1 accounts endpoints, the processing of other smart contract hook executions will be blocked from being processed.With this change, we handle long running hook executions more gracefully, and reduce the likelihood of account smart contract hook executions from being blocked from processing.

 |

TM-85653

 |

 | 

The contract executor can now automatically recover from an exhausted process pool when under heavy load and initiating a restart is not possible.

TM-85208

 | 

Activation Hook example in smart contract common examples is invalid

 | 

In previous versions of Vault Core it was possible for the activation\_hook of smart contracts to create `ScheduledEvents` with no `expression` or `scheduled_method` as long as `skip` was set to True. This made it impossible for Vault Core to schedule the events when they were subsequently unskipped. Validation has now been added so that activation will fail if the hook attempts to create these invalid \`ScheduledEvent\`s. Prior to upgrading to Vault Core 5.1, it is important to use [account conversion](https://docs.thoughtmachine.net/vault-core/5-0/EN/reference/accounts/overview/#account_migrations-standard_account_migrations) to migrate any existing accounts backed by smart contracts that create invalid \`ScheduledEvent\`s.

TM-85415

 | 

Account data fetchers in scheduled\_event\_hook (CLv4) for schedules in a group may retrieve additional postings in different executions of the same job

 | 

Account data fetchers in CLv4 from 5.0 used in scheduled\_event\_hook, guarantee, unless they specify DefinedDateTime.LIVE, that different executions of the same job at different times get the same results.This is however not the case when the fetchers are used by schedules in a group other than the first one.
