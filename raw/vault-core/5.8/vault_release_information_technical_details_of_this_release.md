IMP-1287

 | 

Horizontally scalable internal application cache

 | 

The internal caching solution shipped as part of Vault Core now supports sharding and therefore it can be scaled horizontally.  
  
In Vault Core 5.5+ releases, if you had `ledger.redis_support_pib_caching` enabled OR `.common.deployment_size` set to `medium-large`, then you most likely would have needed to provision a larger Kubernetes node to schedule one of our application’s caches. This is no longer necessary; the cache pods should always be able to fit 64 GB VMs and in most circumstances — 32 GB ones.

IMP-2152

 | 

Additional defaults and improved validation of configuration values during installation

 | 

When generating an example values.yaml configuration file using `vaultctl` more values have recommended defaults. `vaultctl values generate` is now the recommended method to generate the `values.yaml` configuration file. By default the new `generate` sub-command creates a `values.yaml` with only the values requiring manual configuration (those without defaults), but an exhaustive configuration file can still be generated by passing the `--full` flag to the command. Additional validation of these values is carried out during installation and will emit warning on validation failures. Manual validation can be carried out ahead of installation using `vaultctl values validate`. Configuration options are documented in Vault Portal.

TM-112707

 | 

Addresses an issue that could cause compounding Adjustments to use uncorrected balances. When an account requires an Adjustment for a time range that has previously had an Adjustment, and the previous Adjustment resulted in corrective postings for its earliest Adjustment Point, re-evaluation of hook executions up to that first Adjustment Point may not be given a view of postings and balances that reflects the correction postings previously made. This is only possible if the account’s contract creates posting directives outside of Adjustment Point schedules.

TM-113642

 | 

Ensures Adjustments properly account for previous Adjustments' corrections, which could previously cause compounding scenarios to produce inaccurate corrections.

TM-113786

 | 

Addresses an issue where an Adjustment would fail if the timeline included a posting from the adjusted account to another account.

TM-113795

 | 

Prevents Posting Instructions enriched by the Smart Contract via ContractEnrichmentDetails from causing Adjustments to fail.  
Previously, due to erroneous internal validation, Posting Instructions used within an Adjustment were validated as if they were being passed to the pre\_posting\_hook. This validation expects that the enrichment details are empty, because they should only be populated by the pre\_posting\_hook; however, because these instructions are being re-evaluated, they may have had these details set from the pre\_posting\_hook that ran when they were initially accepted.

TM-113798

Addresses an issue where an Adjustment’s corrections would never result in an Adjustment being required on another account despite. This should be possible if:  
\- A customer account is adjusted, and the resulting correction posts to another customer account  
\- The other customer account is on a smart contract with an adjustment strategy  
\- The backdate is a hard backdate, in that it would have been observable by a hook execution that took place, it should trigger an Adjustment.

TM-114126

 | 

Addresses an issue whereby incorrect data could be presented to the ``scheduled_event_adjustment_hook’s `snapshot_vault``, which could lead to inaccurate processing of the Adjustment and incorrect corrections.  
This could happen when:  
\- The original schedule execution was affected by a processing group’s `minimum_observation_timestamp`, a schedule execution for another schedule in the same group, or a delayed previous schedule execution of the same schedule  
\- AND a backdate was inserted after the original schedule execution’s effective time

| 

TM-114561

 | 

When simulating an UpdateAccountV2 instruction that modifies the Parameter Value Hierarchy Node of an account, the post-parameter change hook execution did not correctly populate the old\_parameter\_values field in the hook arguments. Instead of the expected old value, the field appeared empty. The same issue occurred for Adjustments that simulate the post-parameter change hook for a PUT /v2/account request modifying the account’s Parameter Value Hierarchy Node.  
  
This was caused by the simulation not correctly updating the account history, leaving the account data in an invalid state. Since parameter fetching relied on this state, retrieval of the old parameter values returned an empty result rather than the real values. The simulation logic has been corrected to ensure the old\_parameter\_values field is populated as expected.

### [](#asynchronous_executions "Copy link to heading")Asynchronous Executions

 
| Reference | Description |
| --- | --- |
| 
TM-113413

 | 

We identified an issue with contract executions that generate multiple posting instructions. If a timeout occurred while committing them, some instructions could be committed while others were not. When the system retried the execution, it re-fetched live balances instead of replaying the original state. This meant the retry was not fully idempotent, and balances or outcomes could differ from the first attempt.  
  
To reduce the likelihood of this happening, we have adjusted batch sizes and timeout thresholds. In addition, the system now raises a warning if a partial commit occurs, so users are aware of the situation.

 |

 | 

Fixed an issue where Grafana dashboard panels displaying consumer lag metrics did not correctly reflect increases in consumer lag when a Kafka consumer was stuck (not committing offsets). TM-114644

 | 

An Adjustment may produce wrong corrections if all the following conditions are satisfied:  
\- An Account is associated to a Parameter Value Hierarchy node, and obtains values for one or more of its contract’s expected\_parameters from the node  
\- Its contract opts in to the post\_parameter\_change\_hook execution for changes to any of those expected\_parameters  
\- Its contract post\_parameter\_change\_hook returns posting instruction directives  
\- A backdate results in an Adjustment timeline that includes a change to the account’s parameter\_value\_hierarchy\_node\_id. This includes initial association with any node, a change from one node to another, or removal of the association to any node.  

In this scenario the post\_parameter\_change\_hook execution for the parameter\_value\_hierarchy\_node\_id change will not be re-evaluated during the Adjustment computation. This could lead to the Adjustment’s correction postings reversing any original posting instructions, or the Adjustment not producing correction postings when expected.

 |

TM-119109

In Adjustments, any posting directives from the post\_parameter\_change\_hook that result from simulating it for the account activation time will be factored into the applied corrections.  
  
This only happens if:  
\- The adjustment covers the time the account was activated (always the case for an account’s first adjustment)  
\- The account was created with parameter values in the creation request to v2/accounts  
\- The post\_parameter\_change\_hook is used to instruct postings  
\- The contract does not opt out of execution of post\_parameter\_change\_hook for at least one of the values provided at account creation

| Reference | Description |
| --- | --- |
| 
TM-91777

 | 

When making requests to create Parameter values in the data loader, the Parameter value ID is used as an idempotency key, so repeat requests with the same Parameter value ID should have no effect. However, if a second request is sent in with the same Parameter value ID as previously used, but a different request body, then the `effective_to_timestamp` of the Parameter value which:  
  
1\. is effective immediately before; and  
2\. has the same owner as the value in the second request; and  
3\. has the same Parameter ID as the value in the second request  
  
will be incorrectly set to the effective from time of the value in the second request.  
  
This behaviour should be avoided — since Parameter value ID is the idempotency key, requests which reuse the same ID should be identical. If this is the case, this issue will not occur.  
  
If this issue has already arisen, the effective to times of the affected Parameter values can be set manually via the Core API.
