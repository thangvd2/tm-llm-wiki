# Restrictions

The aim of these tutorials is to teach you how to apply restrictions successfully.

## [](#closed_loop_account_tutorial "Copy link to heading")Closed loop account tutorial

A closed loop account (CLA) is an account that can only send payments to, or receive payments from, a nominated bank account. In contrast, an open loop account can send and receive payments to and from any account.

Examples of closed loop accounts are:

-   A saver using a nominated account for deposits into, and withdrawals from, a savings account
    
-   A consumer depositing money to a spending account that is linked to something that can only be used with a specific payee, for example, a gift card for a specific company
    

You can implement CLA functionality using restrictions with exemptions. This tutorial gives an example of how to create a CLA in this way.

### [](#before_you_start "Copy link to heading")Before you start

You will need an open account that has routing information linked to it so it can make payments over a domestic payment scheme. In Vault Core, this routing information is represented by a [\`payment device'](/vault-core/5-8/EN/api/core_api#payment_devices) and the link is represented by a [\`payment device link'](/vault-core/5-8/EN/api/core_api#paymentdevicelink).

### [](#creating_a_cla_using_restrictions_with_exemptions_example_tutorial "Copy link to heading")Creating a CLA using restrictions with exemptions - Example tutorial

This example CLA implementation is based upon three requirements:

-   The account is only able to accept payments from, and send payments to, a specific external account; payments from and to all other external accounts should be rejected.
    
-   Payments between accounts that belong to the same customer should not be rejected.
    
-   Interest paid into, and fees taken from, the CLA should not be rejected.
    

1.  Create a [restriction set definition version](/vault-core/5-8/EN/api/core_api#RestrictionSetDefinitionVersion) preventing all credits and debits at a payment device level (the payment device represents the customer’s UK bank account number).

    `restriction_set_definition_id` in the restriction set definition version and the restriction set (see step 2) must have the same value ("restriction\_set\_id" in this example).
    
2.  Create a [restriction set](/vault-core/5-8/EN/api/core_api#restrictionset) targeting the payment device linked to the CLA. The restriction set points to the restriction set definition version (both have the same `restriction_set_definition_id` value, "restriction\_set\_id" in this example) that is created in the first step.

When a posting instruction is submitted to the Postings API that targets the restricted payment device, Vault applies the restriction and rejects the posting instruction. However, it won’t reject it if the exemption key values match the metadata present in the posting instruction’s [`instruction_details`](/vault-core/5-8/EN/api/core_api#postinginstructionbatch).

Posting instructions submitted to the Postings API by Vault’s Payments Hub include creditor and debitor key values by default (see \`Implementing nominated accounts' in Payments Hub API’s [Payments](/vault-core/5-8/EN/api/payments_hub_api#payments) section).

Payments between same-customer accounts are accepted because they are posted directly to the account, and don’t involve a payment device, meaning the restriction does not get applied.

Interest that is paid to the account, or fees debited, are also accepted because they are generated by Smart Contracts. Smart Contract’s postings to the Postings API target the account’s ID. As this restriction is set at a payment device level, the restriction does not get applied.
